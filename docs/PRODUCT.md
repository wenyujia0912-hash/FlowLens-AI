# FlowLens AI 产品说明

## 1. 产品定位

FlowLens AI 是面向 B2B 电商/企业采购平台内部运营人员的履约异常管理系统。核心思路是：**用确定性规则发现问题，用AI辅助理解问题，用人工决策处理问题，用任务系统追踪闭环**。

产品不做的事：不做商品商城、不做真实ERP/WMS/TMS集成、不做多Agent自主协作、不做AI自动执行外部操作（自动发消息、自动改订单）。

## 2. 核心业务流程

```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐     ┌──────────┐
│  规则引擎    │────▶│  AI诊断(Mock) │────▶│  人工确认    │────▶│  任务服务 │
│ (确定性判断) │     │ (解释/建议)   │     │ (唯一决策点) │     │ (写入)   │
└─────────────┘     └──────────────┘     └─────────────┘     └──────────┘
  产生异常记录        产生诊断记录           采纳/拒绝/编辑        创建任务
  设定初始风险        标注事实vs推测         可改风险等级          关联异常+订单
```

详细步骤：

1. **数据准备**：运行 `seed_data.py` 生成独立模拟数据（40家客户、15家供应商、340条订单，含正常订单和5类异常的正反例）。
2. **异常扫描**：在"AI异常诊断中心"点击"扫描新异常"，规则引擎对全部订单运行5条规则判断，命中且未重复的违规会创建异常记录。
3. **事实查看**：进入异常详情，"已知事实"区展示触发该异常的具体字段值（例如"预计发货时间=X，当前时间=Y"），这部分**不经过AI**，是数据库里的真实字段。
4. **AI诊断**：点击"运行AI诊断"，Mock AI基于已知事实生成摘要、可能原因（标注置信度）、客户影响分析、建议措施、沟通参考文本、待核实事项。
5. **人工核实**：运营人员查看诊断，可以修改风险等级、勾选采纳哪些建议。
6. **创建任务**：填写负责人、优先级、截止时间，提交后任务与异常/订单建立关联，异常状态自动变为"处理中"（这是明确的人工动作触发的联动，不是AI自动做的）。
7. **任务处理**：负责人更新状态、追加处理记录（时间线，不覆盖历史），完成时必须填写处理结果。
8. **数据回流**：驾驶舱和运营分析页面的全部统计数字都是数据库实时查询结果，任务完成、异常状态变化都会立即反映在统计里。

## 3. 功能模块

### 3.1 运营驾驶舱

展示：订单总量、异常订单数、待处理异常数、履约完成率、逾期任务数（KPI卡片，点击跳转对应列表）；订单量趋势图；异常类型分布；风险等级分布；待办任务列表（逾期或高优先级）。

### 3.2 客户与订单管理

客户列表（搜索+行业/等级/状态筛选）、客户详情（关联订单和异常数量由数据库实时关联计算）；订单列表（编号搜索+多维度筛选）、订单详情（商品明细、履约时间线、供应商信息、物流节点、关联异常）。

### 3.3 AI 异常诊断中心

**这是系统的核心模块。** 支持的5种规则：

| 规则代码 | 异常类型 | 判断条件 |
|---|---|---|
| SHIP_OVERDUE | 超时未发货 | 当前时间超过预计发货时间，且未发货、订单未取消 |
| DELIVERY_STALLED | 物流延迟 | 物流最后更新时间超过配置阈值（默认48小时），且未签收 |
| DELIVERY_OVERDUE | 履约超时 | 实际签收时间晚于预计送达时间 |
| SUPPLIER_PREP_DELAY | 供应商备货异常 | 供应商备货状态更新时间超过配置阈值（默认72小时）仍未完成 |
| STATUS_CONFLICT | 订单状态异常 | 订单状态与物流状态命中预定义的不合理组合 |

异常详情页严格分四区展示，这是本模块最重要的设计约束：

- **📋 已知事实**：触发规则、关键字段值——来自规则引擎，不经过AI
- **🤖 AI诊断（推测）**：摘要、可能原因（每条标注置信度 低/中/高）、客户影响分析——这是AI的归纳，不是确定结论
- **✅ 建议操作**：AI给的处理建议和沟通参考文本，需人工勾选采纳，不会自动执行
- **❓ 待核实事项**：AI没有把握、需要人工核实的信息，纯展示，不可操作

### 3.4 运营任务中心

任务列表（状态/优先级/负责人/截止时间筛选）、任务详情（关联异常/订单的反向跳转、处理记录时间线、状态更新）。核心约束：完成任务必须填写处理结果（服务层+数据库CHECK约束双重保证）；任务日志追加式记录，不覆盖历史；任务状态变化不会自动改变关联异常的状态。

### 3.5 运营分析

履约分析（完成率、平均履约时长、延迟订单占比）、异常分析（类型分布、风险分布、重点客户异常情况）、任务分析（完成率、平均处理时长、逾期数），均支持查看明细和导出Excel。

## 4. AI 能力与人机协同机制

### 4.1 AI 的职责边界

| 能做 | 不能做 |
|---|---|
| 基于规则引擎提供的事实生成摘要、原因归纳、建议 | 自己判断"这是不是异常"（那是规则引擎的职责） |
| 标注每条原因的置信度 | 把推测包装成确定事实 |
| 生成供参考的沟通文本 | 自动发送任何消息给客户/供应商 |
| 产出结构化的诊断记录 | 直接写入/修改订单、物流、异常的状态 |
| | 在没有人工确认的情况下创建任务 |

### 4.2 当前 AI 实现：Mock

当前系统**没有接入任何真实大模型**，`AI_MODE` 固定为 `mock`。Mock的实现方式：针对5种规则代码各维护一套中文模板（摘要句式、2条可能原因、客户影响分析、建议措施、沟通文本、待核实事项），根据具体订单的字段值填充模板中的占位符（如订单编号）。

这不是"假装AI"——Mock输出严格遵循与真实LLM输出完全一致的JSON schema（`summary`/`possible_causes`/`customer_impact`/`risk_level`/`priority`/`recommendations`/`communication_draft`/`verification_required`），且经过与真实Provider共用的同一套校验函数。业务层代码完全不知道、也不需要知道当前是Mock还是真实模型。

选择暂不接入真实LLM的原因：当前阶段优先验证业务闭环的正确性和控制开发成本，Mock已经能完整演示"事实→推测→建议→确认"的人机协同模式。真实AI接入方式见 [ARCHITECTURE.md](ARCHITECTURE.md)。

### 4.3 为什么这个边界很重要

B2B运营场景里，AI给出错误建议的代价不是"回答得不好"，而是可能影响真实的客户关系和运营决策。把"确定性判断"和"辅助推测"分开、把"生成建议"和"执行动作"分开，是让AI在这类场景里可用、而不是必须每次都assume AI对的前提。
